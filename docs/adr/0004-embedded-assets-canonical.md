# ADR 0004: Embedded assets are the single canonical source of project config

**Date:** 2026-07-01
**Status:** Accepted

## Context

`orq-lite init` scaffolds a project from assets embedded in the binary at
`internal/commands/assets/` (`team.json`, `prompts/*.md`, `schemas/*.json`).
The orquestalite repository also dogfoods its own tooling: a `team.json`,
`prompts/`, and `schemas/` at the repo root let an agent run `orq-lite` against
the orquestalite codebase itself.

Two distinct asset sets existed and got mixed:

1. **Package assets** (`internal/commands/assets/`) — the canonical, embedded
   source `init` scaffolds from. Complete and healthy.
2. **Dogfooding config** (repo root: `team.json`, `prompts/`, `schemas/`) —
   runtime config to run orq-lite on its own repo; intentionally gitignored and
   legitimately divergent from the assets (e.g. `lint_command: "go vet ./..."`).

A hybrid bug existed: a stale, partial snapshot of the dogfooding config was
force-tracked into git (9 of 14 prompts, a `team.json` without the `generalist`
role). A fresh clone therefore received incomplete dogfooding config — the worst
of both worlds: not regenerated (because it was tracked), and incomplete
(because it was a snapshot).

## Decision

The **dogfooding config is generated, not tracked.** The only versioned source
of truth is the embedded `internal/commands/assets/`. Concretely:

- `team.json`, `prompts/*.md`, and `schemas/*.json` at the repo root are
  untracked (removed from the index) and remain gitignored. They are
  regenerated by `orq-lite init` after a fresh clone.
- The `.gitignore` keeps the repo-wide ignores for `prompts/` and `schemas/`
  but allows the embedded assets through with negation patterns
  (`!internal/commands/assets/prompts/**`), so the binary's source stays
  trackable while the dogfooding copies don't.
- `examples/` remains the documented exception: each example ships a complete,
  runnable, **tracked** config so users can copy a working setup wholesale.
  These are not dogfooding; they are shipped reference configs.

## Consequences

- A fresh clone no longer carries stale dogfooding config; `orq-lite init`
  regenerates it from the embedded assets (which are the same files the
  release binary scaffolds for any project).
- Contributors regenerate their root config locally; they never commit it.
- The embedded assets are the single place to change default scaffolding for
  all users — there is no second copy to drift.
- `doctor` and `intake`/`watch --issues` work on a fresh clone because the
  embedded assets are complete (including `prompts/intake.md`, fixed in the
  same change set).
